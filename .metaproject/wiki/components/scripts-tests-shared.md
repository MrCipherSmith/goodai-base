# Module scripts/tests/shared

## Overview

`scripts/tests/shared` is the unit test module for the shared utility library defined in `scripts/src/shared`. It contains six test files, each covering a distinct utility: agent markdown parsing, argument handling, checksum computation, frontmatter management, file system helpers, and keyword extraction. The module’s purpose is to verify the correctness and robustness of these core functions, ensuring they behave as expected across normal and edge cases.

## How it works

Each test file imports the corresponding source module from `scripts/src/shared` and exercises its public API using assertions. The tests are structured to cover typical usage, boundary conditions, and error scenarios. The test runner (vitest or jest) discovers all `.test.ts` files under `scripts/tests/shared` and executes them as part of the project’s continuous integration pipeline. The module does not introduce any runtime abstractions of its own; it is purely a validation harness.

## Key concepts

- **Utility‑under‑test** – Each test file targets exactly one exported module from `scripts/src/shared` (e.g., `frontmatter`, `args`, `checksum`).  
- **Test case** – A single assertion or group of assertions that verifies a specific behavior of the utility.  
- **Fixture** – Test data (e.g., sample markdown text, command‑line arguments) that is passed to the utility to produce a known result.  

These concepts are not new domain vocabulary; they are standard testing practices applied to the shared utility set.

## Main flows

1. **Full test suite execution**  
   The developer runs `npm test` (or equivalent). The test runner scans `scripts/tests/shared`, finds all six `.test.ts` files, imports each, and runs every test case. A summary of passed/failed assertions is printed.

2. **Frontmatter parsing test flow**  
   In `frontmatter.test.ts`, a test calls `parseFrontmatter('---\ntitle: Test\n---\nBody')` and asserts that the returned object equals `{ title: 'Test' }`. Similar tests cover malformed frontmatter, missing delimiters, and empty strings.

3. **Check‑sum computation test flow**  
   In `checksum.test.ts`, a test computes an SHA‑256 checksum of a known string and compares it against a pre‑computed hash. Edge cases include empty input and Unicode characters.
